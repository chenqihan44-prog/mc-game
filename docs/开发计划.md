**1．产品目标与范围**

制作一款第一人称、单人离线、可持续保存的体素沙盒游戏。玩家从荒野建立营地，进入洞穴寻找材料，制作装备，修复古代灯塔，逐步把自己的基地发展成探索据点。保留自由挖掘、搭建与改造地形的开放性，同时提供可选择的探索目标。

首版优先级顺序：操作与反馈 → 世界和存档可靠性 → 生存循环 → 探索与建造内容 → 视觉和声音统一。所有玩家可见系统都必须具有正常、失败、退出重进后的完整行为。

| 维度 | 1.0 目标 | 验证方法 |
| --- | --- | --- |
| 易上手 | 新玩家在 10 分钟内独立完成采集、制作工具、放置营火 | 5–8 名外部试玩者观察记录，目标至少 80% 完成；属于小样本体验检查 |
| 生存闭环 | 白天准备、夜间生存、探险、升级、返回营地形成循环 | 完整体验首个昼夜，不使用调试命令 |
| 探索动力 | 建议目标路线提供约 6–10 小时内容 | 记录不同经验玩家的实际耗时并调整，不以重复采矿凑时长 |
| 建造自由 | 地表与地下可编辑，支持建筑构件、装饰和创造模式 | 独立完成住房、仓库、农田与桥梁并保存恢复 |
| 重玩差异 | 种子改变地形、资源、建筑位置与探索路线 | 固定测试种子与随机种子回归 |
| 完整产品 | 主菜单、世界管理、设置、暂停、死亡、存读档、帮助齐全 | 从首次启动到退出重进的发布包验收 |

默认假设：简体中文界面；键鼠操作；像素风材质与简洁立体生物；没有账号、联网依赖和付费系统。采用原创或许可明确的素材，并保留来源清单。首版操作范围为键鼠；手柄、其他语言及其他系统属于后续版本。

明确后续范围：多人联机、复杂电路、大规模自动化、动态流体、载具、村民经济、多个世界维度、模组平台、季节生态模拟、移动端。这些功能不作为 1.0 的交付依赖。

**2．游戏循环与成长设计**

基本循环：发现地点 → 准备工具和补给 → 采集或战斗 → 带回资源 → 改善基地与装备 → 前往新的地点。

每次出门至少提供一种有意义的选择：走安全路线还是捷径；优先带食物还是建筑材料；继续深入还是带着收获返程。奖励同时服务建造和探索，避免只有武器数值在成长。

| 体验阶段 | 玩家行为 | 阶段奖励 | 需要检查的问题 |
| --- | --- | --- | --- |
| 0–5 分钟 | 观察附近环境，捡拾枝条与碎石，制作简易工具 | 能主动获取木材与石料 | 开局材料不可依赖尚未制作的工具 |
| 5–15 分钟 | 制作工作台、营火，建立小屋并烹饪 | 夜间安全感与食物来源 | 不用查外部教程也能完成 |
| 15–40 分钟 | 进入浅层洞穴，获取铁矿与燃料 | 铁制工具、储物与冶炼 | 资源分布不迫使玩家漫无目的挖掘 |
| 40–120 分钟 | 扩建营地、种植、探索第一个遗迹 | 地图线索、建筑配方、灯塔修复材料 | 建家与探险能互相提供收益 |
| 2–6 小时 | 探索不同生态区，修复更多灯塔，取得晶矿 | 高阶工具、装饰材料、快速返程 | 升级改变行动方式，避免只增加耐久 |
| 6–10 小时 | 挑战遗迹守护者、完成灯塔网络 | 完整探索目标与纪念性建筑内容 | 目标完成后仍能自由继续建造 |

以上时间是节奏设计假设，不是强制关卡；允许玩家一直建造、提前探险、跳过战斗目标。

核心特色采用“营地与灯塔”系统：床设置复活点；营火附近提供清晰标记的有限安全区；古代灯塔修复后显示该区域的重要线索，并开启已激活灯塔之间的旅行。快速旅行需要在灯塔处发起，脱离战斗且消耗普通燃料，降低中后期重复赶路。地图里必须存在可达的三个目标灯塔，生成失败时使用确定性的保底布局。

成长分三档：石器 → 铁器 → 晶矿工具。高阶工具除了效率提升，还提供特定矿物采集或更便利的建造能力。基础建筑材料保持易得，特殊材质作为探索奖励。配方以材料发现和遗迹线索逐步提示；已知配方可以检索、收藏并查看缺失材料。

标准难度下死亡留下可取回的背包，不再因第二次死亡删除前一个背包；已放置建筑、地图发现和解锁永久保留。休闲难度允许保留物品并减轻饥饿。难度和死亡规则在创建世界时清楚展示。避免加入需要频繁处理的口渴、疾病等额外生存条。

**4．世界规模和生成规则**

首版世界目标为水平 4096 × 4096 格、高度 192 格，有明确边界，通过远处山脉、海域与边界提示表达。内部使用整数体素坐标，探索时逐步生成和加载，不一次分配整个地图。世界可选择种子，并提供若干经过验证的推荐种子。

分块初始方案：每个数据区块为 X16 × Y32 × Z16 格；竖直六块组成一个地形柱。具体尺寸允许在第 1 阶段基准测试后调整。中画质初始视距为半径 8 个地形柱，提供 4/6/8/12 档选择；碰撞和生物模拟范围小于显示范围。

生成顺序为：种子和生成器版本 → 高度与气候字段 → 生态区 → 洞穴 → 矿脉 → 跨区块建筑 → 地表植被 → 出生点校验。随机数由种子、坐标及生成阶段共同派生，不能依赖线程完成顺序。

跨区块树木和建筑使用确定性的所属区域与放置记录，避免重复和截断。出生区必须有可站立地面、木材、石料、可获得的食物和一条安全离开路线；必需矿物与灯塔检查失败时采用有边界的重试和保底生成。

湖泊与河道采用静态水体，支持游泳、岸线和水下反馈。首版不实现水桶搬运与动态流动；世界规则与界面保持一致。雨雪只作为表现与氛围，不触发复杂积雪或侵蚀模拟。

白天、夜间、天气通过可保存的世界时间推进。暂停单人游戏时停止模拟；未加载区域的农作物和熔炉依据世界时间补算，并设置合理上限。生物 AI 在远处停止实时运行，不按系统时钟模拟离线战斗。

**5．技术选型与代码结构**

建议采用 Godot 4 的稳定 .NET 版本、C#、Windows x64 导出。Godot 官方提供 Windows .NET 编辑器与导出模板，C# 支持桌面平台；普通版编辑器不包含 C# 支持。开工时锁定编辑器、SDK、导出模板与依赖版本。[Windows 官方下载](https://godotengine.org/download/windows/)；[C# 官方说明](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/index.html)。

采用 C# 是本项目的工程选择：用同一语言编写紧凑数组、生成与网格计算、背包规则和界面行为，便于直接测试纯数据模块。这不是引擎性能保证，仍需测量体素场景。

当前环境探查：找到 dotnet 可执行文件，但 `dotnet --list-sdks` 未列出 SDK；命令路径中未找到 Godot。首个阶段应核验或准备开发工具。本次硬件信息读取未成功，因此性能参考机不是已确认的本机配置。

**6．体素性能与交互一致性**

体素存储采用紧凑数组与空区块优化。按区块生成网格，只绘制暴露面；不透明面使用贪心合并，按材质、方向、光照和遮蔽信息判断是否可合并。台阶、门等非完整方块采用专用模型模板；叶片裁切材质与水、玻璃等透明材质分离处理。不能给每个普通方块建立独立节点或刚体。

计划用 ArrayMesh 提交程序生成的顶点与索引；该 API 支持由数组构造网格，但区块调度和面合并需要项目自行实现。[ArrayMesh 官方文档](https://docs.godotengine.org/en/stable/tutorials/3d/procedural_geometry/arraymesh.html)。

生成、网格构建和压缩由受限工作队列处理；工作线程接收不可变快照，输出纯数据。场景树操作、图形资源提交与碰撞应用在主线程执行。Godot 官方明确活动场景树并非线程安全，因此不让后台任务直接修改它。[线程安全官方文档](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)。

区块任务记录世界会话 ID、区块坐标、区块修订号及相邻边界版本。玩家修改方块、切换世界或卸载区块后，过期结果必须丢弃；任务队列、待提交数据及缓存都设上限，避免高速移动时持续积压。

编辑世界采用主线程校验与有序提交。背包扣除、世界变更、碰撞和可见网格必须有明确的事务边界；跨区块修改同时标记邻居。首个技术样板验证“临时近场碰撞代理”方案，或选择同一物理帧应用已就绪的网格和碰撞；方案确定后固定一种实现。反馈可以即时播放，正式交互结果必须与实际碰撞一致。不得让角色走入数据或碰撞尚未就绪的区域。

寻路以附近体素可行走空间为基础，设置搜索节点和时间预算；地形修改使相关路径失效。远处生物降低更新频率。起始预算为最多 48 个活跃生物，掉落物邻近合并，针对极端堆积设清晰且可测试的处理规则。

光照优先采用太阳光、环境光、顶点遮蔽，以及数量受控的近场光源；灯具的发光表现与真实动态光源数量分离。首版不实现完整体素光传播。洞穴可读性、夜晚氛围与性能在试玩中共同调整。

**7．存档和数据可靠性**

存档放在用户可写的应用数据目录，按世界 ID 隔离。每个世界保存种子、生成器版本、数据格式版本、玩家状态、物品与容器、变化区块、时间、作物和熔炉、探索及灯塔状态。只保存相对于原始生成的修改；修改密集时转为压缩的完整区块快照。

自动保存初始周期为 60 秒，并在主动保存、正常退出和重要进度节点触发。界面显示保存状态、上次成功时间及可理解的错误；磁盘满或权限问题不得伪装成保存成功。

跨文件一致性采用保存代际：在统一模拟时刻获取快照，写入新的变更区域和玩家文件，完成校验及落盘后提交指向该代际的清单；未变区域引用之前的有效版本。不能只分别覆盖玩家文件和区块文件，否则崩溃可能复制或吞掉物品。

使用临时文件、校验和、可恢复的提交记录与最近三份有效备份；切换提交指针的具体文件操作在目标 Windows 文件系统上做中断测试。恢复承诺限定为“恢复到最近一次完整提交”，不承诺保存尚未提交的每个动作。磁盘或硬件损坏超出普通自动保存保证范围。

测试至少在写区块、写玩家状态、写清单与提交期间强制结束进程。重新启动时选择完整代际，报告恢复发生，保留损坏文件以便定位，不能静默创建空白世界覆盖旧档。

生成器升级保留旧世界对应的算法版本；需要变更时提供显式迁移与备份，不使用新生成器直接套用旧差分。存档格式迁移有版本链和回归样本；不支持的未来版本给出提示并拒绝写入。

**8．画面、音效与使用体验**

美术采用统一像素密度、有限色板与清晰轮廓；自然环境偏柔和，矿物、交互物与敌人轮廓更易辨认。先完成一小套最终品质的材质、生物与界面样板，再扩充内容。场景包括远景雾、昼夜色调、水面、雨雪和轻量粒子，提供性能开关。

声音覆盖不同材质脚步、敲击、破坏、拾取、界面、制作、生物预警与环境。战斗提示同时提供视觉信号，关键状态不依赖颜色或声音单一通道。环境音乐适当留白，避免长时间循环疲劳。

玩家设置包括分辨率、窗口模式、视距、阴影、帧率限制、音量分类、灵敏度、视野、按键重绑定、界面缩放，以及关闭镜头摇晃和受击闪烁。暂停时释放鼠标，返回游戏再捕获；切换窗口不继续误攻击。

新手引导是可以跳过、可再次查看的短目标：拾取材料 → 制作工具 → 建营火 → 储物 → 安全过夜 → 找到首个洞穴。失败时提示直接相关原因，例如缺少材料、空间被占用或工具等级不足。

**9．实施顺序、交付物与阶段关卡**

每一阶段都有可运行交付物；阶段关卡不通过时，先解决问题再扩大后续内容。存档与性能从前期进入，不留到项目尾声。以下为 9 个有序工作包。

| 阶段 | 工作与交付物 | 验收关卡 | 粗估工作量 |
| --- | --- | --- | --- |
| S0 固定工程与风险样板 | 锁定 Godot/.NET/导出版本；创建工程、输入和基准场景；完成第一次 Windows 导出 | 发布包在非编辑器环境启动；记录基准硬件、渲染器和测试参数 | 16–24 小时 |
| S1 完成体素核心 | 区块、可见面网格、流式加载、移动碰撞、拆放与最小保存；交付首个可操作 EXE | 跑跳拆建连续 30 分钟；跨区块编辑正确；退出后建筑存在 | 64–96 小时 |
| S2 做出完整玩法样板 | 背包、配方、工具、营火、熔炉、生命、饥饿、昼夜、一种敌人、死亡；加入一处遗迹样板 | 无调试命令完成采集→工具→营地→采矿→升级→探险→死亡/返回→重进 | 64–96 小时 |
| S3 完成世界与持久化 | 四种生态区、洞穴、矿物、遗迹规则、出生保障、跨文件存档、版本与备份 | 固定种子确定性、出生可用性与存档中断测试通过 | 80–120 小时 |
| S4 完成生存探索成长 | 六种生物、战斗、种植、三档工具、三座灯塔与守护者目标 | 从新世界到目标完成可达；没有必须使用调试工具解除的卡点 | 80–120 小时 |
| S5 完成建造内容 | 达到方块、物品和配方预算；完善楼梯门窗装饰、容器及创造模式 | 完整建造住房/仓库/农场；所有配方与容器操作可用且可保存 | 56–88 小时 |
| S6 完成产品与视听 | 统一素材，完善主菜单/设置/世界管理/帮助/引导，补齐音效与反馈 | 使用发布包可独立完成所有常用流程，无占位功能 | 72–112 小时 |
| S7 完成试玩与性能收敛 | 开展外部试玩，调节节奏，优化生成/提交/AI/透明物体，进行耐久与回归测试 | 达到下文发布指标，已知缺陷分级并关闭阻断项 | 96–144 小时 |
| S8 打包并验收候选版 | 导出 Windows x64 包、源码、运行说明、素材许可、测试报告和已知限制 | 干净用户环境启动；旧档与新档均能使用；完成 90 分钟发布包验收 | 24–40 小时 |

依赖关系：S0 → S1 → S2 是玩法和性能决策点；通过后再进入 S3–S6 的内容建设；S7 可提前积累测试，但正式收敛要等内容冻结；S8 必须通过全部发布门槛。可在逻辑稳定时穿插素材制作，不假设存在额外开发人员。

工作量合计约 552–840 小时，另留约 25% 风险缓冲后为 690–1050 小时。以一名熟悉 3D 游戏开发的开发者每周 35 小时有效投入计算，约 20–30 周；这是人工等效工作量估算，不是交付承诺。原创模型、声音全部重做，或追加联机，会增加工期。S0/S1 完成后根据实际测量重新估算。

首个可操作版本目标落在 S1；能检验可玩性的完整样板落在 S2。样板范围约为一个生态区、12 种方块、8 条配方、一种敌人、一处遗迹和可靠的最小存档。玩法未成立时不提前填满 90 个物品。

**10．验收场景与发布门槛**

性能参考配置暂设为 i5-10400 级 CPU、GTX 1650 级显卡、16 GB 内存、SSD；这不是已读取的本机配置。使用 Release 导出包、1080p、中画质、半径 8 个地形柱测试。不同硬件的支持范围以最终实测为准。

| 检查项 | 初始发布目标 | 测量约束 |
| --- | --- | --- |
| 常规游玩 | 平均 ≥60 FPS，95% 帧耗时 ≤22 ms，99% 帧耗时 ≤50 ms | 固定种子，预热后分别采样步行、疾跑、建造、战斗各 5 分钟 |
| 生成/保存卡顿 | 不出现可重复的 >100 ms 主线程冻结 | 连续进入新区、批量修改与自动保存同时进行 |
| 地形编辑 | 点击反馈立即出现；正常负载下碰撞与画面完成更新 ≤100 ms | 单次编辑与持续拆放分别记录分布 |
| 首次进入 | 新世界 ≤15 秒，已有常规世界 ≤8 秒 | 记录冷启动/热启动，统一 SSD 测试条件 |
| 内存 | 常规场景总进程占用 ≤2.5 GiB | 30 分钟探索后回到起点，缓存回收后不持续增长（按用户要求调整） |
| 世界可靠性 | 100 个固定种子生成检查通过，另抽查随机种子 | 验证资源、边界、出生区和目标可达性 |
| 保存恢复 | 所有设计的中断注入点可恢复上一完整保存 | 包括容器转移、合成、跨区块修改与死亡状态 |
| 物品守恒 | 不出现复制或无规则损失 | 拆分、交换、溢出、丢弃拾取、关界面、死亡和读档组合测试 |
| 稳定性 | 30 分钟自动巡游与 30 分钟人工耐久游玩不崩溃 | 按用户要求调整；覆盖区块卸载、怪物活动和持续保存 |

性能不达标时依次降低不必要的动态灯光、阴影与透明特效，缩小默认视距，优化任务批量与网格，再依据测量调整区块大小或移植计算热点。不能以减少碰撞或存档正确性换取帧率。

自动化测试重点放在容易造成真实损失的逻辑：负坐标及区块边界换算、随机生成确定性、网格边界、物品转移与合成事务、保存回读和版本迁移、任务过期取消。不为每个简单界面样式编写大量镜像测试。

外部试玩至少进行两轮：S2 验证循环和引导；S6–S7 验证长时动力、挫败感与建造便利性。目标为 5–8 名不同经验的试玩者；须实际招募并取得反馈，不能把模拟评审视为真人结果。记录首件工具/首夜/首个遗迹的完成时间、死亡原因、停滞点与是否愿意继续。人数少时明确其结论局限。

最终人工验收路径：创建世界 → 制作工具与营火 → 建造可关闭的小屋 → 放置并操作箱子/熔炉 → 过夜 → 采矿升级 → 发现遗迹 → 受伤并恢复 → 死亡找回背包 → 扩建房屋和种植 → 保存退出 → 重开后核对地形/物品/进度 → 在创造模式完成独立建筑。灯塔与守护者完整成长路线另用新档验证，不能仅靠后期测试存档跳过前置。

发布阻断项：启动失败、崩溃、存档损坏、物品复制、掉入未加载地形、关键流程无法继续。其余缺陷按严重性处理，已知限制必须在交付说明中清楚描述。性能与体验目标未实测前只标记“待验证”。

**11．主要风险与处理规则**

| 风险 | 早期信号 | 处理措施 |
| --- | --- | --- |
| 范围失控 | 核心循环未稳定却不断追加系统 | 冻结内容预算，把新想法放入 1.1 清单 |
| 世界性能不足 | 普通地形就无法保持预算 | S1 阶段先优化或调整分块，暂停内容扩张 |
| 存档不一致 | 物品和方块恢复到不同时间点 | 统一快照与代际提交，增加中断回归 |
| 探索重复 | 玩家只沿直线挖矿、忽略遗迹 | 调整地标密度、资源线索与不同路线的收益 |
| 生存繁琐 | 大量时间用于补饥饿与重复赶路 | 调整食物收益，改善早期种植和灯塔旅行 |
| AI 受地形修改破坏 | 卡墙、穿墙、追逐震荡 | 小范围路径更新与预算，保留可靠的撤退行为 |
| 素材不统一 | 不同来源的色彩和像素尺度冲突 | 先定样板与规范，扩充时统一修整 |
| 开发机与玩家环境不同 | 编辑器可用而发布包异常 | 从 S0 开始导出，并在干净用户环境回归 |

如需压缩工期，优先减少方块装饰变体、天气表现和遗迹模板数量；保留存档、操作反馈、完整界面和一条可完成的成长路线。多人联机若成为确定需求，应重新估算权威状态、同步与网络测试工作，不能简单当成末尾附加按钮。

**12．交付清单与下一步**

1. 可双击运行的 Windows x64 游戏包，具备真实可用的生存和创造模式。
2. 完整 Godot/C# 工程、锁定版本信息和构建脚本。
3. 游戏玩法、控制、设置、存档备份恢复和常见问题说明。
4. 数据配置、素材来源及许可清单。
5. 性能报告、测试种子、关键回归结果和已知问题列表。
6. 一份示例世界，可展示住房、农田、仓库和探索进度；同时保留新建世界的完整体验。

实施起点为 S0：确认可用 Godot .NET 与 SDK 版本，建立可导出的空工程与体素基准场景；随后完成 S1 的走动、拆放、碰撞与最小存档。计划文件完成不代表游戏实现完成。
